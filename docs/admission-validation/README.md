הבדיקה מריצה את `src/modules/calculators/index.ts` שבמוצר מול 29 תשובות רשמיות שנשמרו עם אותם פרופילים סינתטיים, קובצי תגובה גולמיים, רשומות קלט ו-SHA-256. אין קריאות AI או HTTP. היא משווה כל ספרה ושדה, גם כששדה חסר במוצר. תוצאות המחקר המקוריות נשמרות ללא שינוי תחת `verification/research/`; התאמת נתיבים מתבצעת בזיכרון בלבד.

בבראנץ׳ הזה יש **25/29 התאמות מספריות**, כולל **20/20 בטכניון**, לעומת 18/29 בקוד הבסיס. שלושה מקרי ת״א חסרים `exactSciencesSekem` ו-`medicinePreliminary`; ברייכמן A נותר 739.12 לעומת 739.13. הממוצעים ודוגמאות הסכ״ם אינם מוכיחים את כל הקלטים, סוגי התעודות או מסלולי הקבלה. לכל 29 התשובות חסרה ראיה לשנת הלימודים של אותה פונקציית מחשבון: **אפס מקרי אימות עדכני מלא**. אין היתר פרסום אוטומטי.

## הרצה

נדרשים Node 25.6.1, Python 3.9+ ו-`npm ci`. Python משתמש בספרייה הסטנדרטית בלבד; `jiti` ו-`tsx` נעולים בתלויות הפיתוח. אין צורך ב-DB, מפתח API או ציוני מועמד אמיתי לבדיקה הזאת.

```sh
npm run admissions:test
npm run admissions:check -- --cadence daily
npm run admissions:check -- --cadence weekly
npm run admissions:regression
```

`admissions:check` מחזיר כעת 2 ו-`review_required`: זה דוח שצריך טיפול, לא אישור שהכול מדויק. `admissions:regression` מחזיר 0 רק כשהתוצאה ההיסטורית המלאה זהה ל-baseline שנבדק ואין בעיית שלמות. **הצלחה ב-CI אינה אישור התאמה רשמית עדכנית.** ה-baseline משאיר את ארבעת הכשלים גלויים; הוא אינו מעגל אותם או משמיטם. ראיות שמתיישנות מעבר לשבעה ימים דורשות חידוש ולא מקבלות תאריך איסוף חדש באופן מלאכותי.

הדוח `.admission-validation/latest.json` נכתב באופן אטומי, כולל סימון `running` בתחילת הריצה. שגיאה מחליפה דוח הצלחה ישן. הוא כולל לכל מקרה expected/actual, דיוק, חוסר שדות, שנת מקור, שגיאות, hash של המוצר ומיפוי הכיסוי. `source_freshness: not_observed_offline` פירושו שלא נבדק עכשיו אם המוסד שינה את המחשבון. אין דיווח שגוי על "המוסדות לא השתנו".

## תזמון ללא AI

ההרצה משתמשת בבתים שנקראו ואומתו, מתוך snapshot זמני ומבודד של קוד המוצר, התלויות והראיות. ה-guard מקומפל מאותם בתים ב-namespace פרטי, ללא ייבוא חוזר מהדיסק או שימוש ב-module cache קיים. החלפת קובץ ב-checkout בזמן הריצה אינה מחליפה את הקוד או ערכי ההשוואה שנבדקו. הדוח מזהה את גרסת המקור שנלכדה בתחילת הריצה; הריצה הבאה מזהה שינוי מתמשך ב-checkout.

`.github/workflows/admission-regression.yml` מפעיל רגרסיה ב-PR, בהרצה ידנית, ואחת לשבוע ביום שני ב-02:17 UTC לאחר שהתצורה תגיע לענף ברירת המחדל. הוא משתמש ב-runner רגיל; בריפו ציבורי GitHub מציין שהשימוש חינם ([תיעוד GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job)). התצורה על הבראנץ׳ אינה התקנת תזמון בפרודקשן. לתדירות יומית אפשר לשנות את שורת ה-cron ל-`17 2 * * *` במסגרת PR. ההרצות אינן ניגשות לאוניברסיטאות; הן בודקות שהקוד והראיות שנבדקו עדיין תואמים, ושכיסוי הקטלוג לא השתנה ללא סקירה.

אפשר להריץ את אותן פקודות ב-cron בשרת הקיים של שגיא, מתוך checkout ייעודי עם תלויות פיתוח, ללא חיבור ל-DB של המוצר. לדוגמה שבועית:

```cron
17 2 * * 1 cd /absolute/path/to/kalis && npm run admissions:check -- --cadence weekly --output /absolute/path/to/reports/admissions-latest.json
```

אין לשנות pins או baseline אוטומטית. שינוי נוסחה, parser, ראיה, קטלוג או תלות עוצר את ההרצה. הצעת שינוי צריכה ראיה רשמית חדשה, אותה זהות קלט, דיוק ושנת מקור, בדיקות וסקירה עצמאית של ה-tree וה-parent לפני עדכון `verification/binding.json` / `numeric-baseline.json` / `coverage.json`. ה-hashes מזהים שינויים ביחס לבראנץ׳ שנבדק; אינם חתימה קריפטוגרפית על אישור אנושי.

## חידוש מול המוסדות

השלב הזה עדיין דורש חיבור מוגן של האיסוף החי לריפו. אין לתזמן את `scripts/verification/verifyOfficialCalculators.ts` הישן: הטולרנסים שלו מסתירים ספרות, אין shared budget/holds ותשובת כשל עלולה להשאיר את הדוח הקודם. המסלול החי הקיים במחקר משתמש ב-`admissions_guard` Collector/State וב-`integration/maintenance.py`; חבילת המחקר שנמסרה היא `sagi-admission-validation-33-components-final.zip`, SHA-256 `de7524b567d70f6b3c653d9837c04a205fae64762a8e19241689eaa3a90a211f`.

לפני איסוף חי חייבים לחבר את **אותו SQLite מתמשך ומיושב** לכל worker ותדירות, כולל aliases, ספירת הבקשות וה-holds מהמחקר. קובץ DB חדש, cache של runner או יום חדש אינם היתר להסיר hold. במחקר נותרו 15 קבוצות עם hold; אין עוקפים CAPTCHA, משנים זהות/IP, מגדילים קצב או מאפסים ספירה. robots/היתר מקור, timeout, מספר בקשות מקסימלי, spacing, Retry-After, backoff, שמירת תגובות גולמיות וראיות קלט/פונקציה/שנה נבדקים לפני השוואה. מרווח אקראי יכול להפחית עומס, ואינו מבטיח מניעת חסימה או מאפשר עקיפת איסור.

תשובה חדשה נשמרת כראיה חדשה; שינוי hash של HTML אינו בהכרח שינוי נוסחה. קודם מפרידים שינוי תוכן/מבנה/גישה, ואז מריצים את אותם מקרים ומשווים שדות מספריים ותשומות. אי-אפשר לאשר עדכון אוטומטי לכל נוסחה סגורה או לכל אתר משתנה. בהיעדר גישה או כלל חד-משמעי, הדוח נשאר חסום/לא מאומת. אף נוסחה לא מתעדכנת מהתאמה סטטיסטית לכמה דוגמאות.

ראו [מיפוי הכיסוי](COVERAGE.md) לכל 62 המוסדות, הפונקציות והפערים. סוגי תעודות אחרים, קבלה ללא פסיכומטרי, מקצועות עמומים, נתוני DB ומסלולי optimizer/UI עדיין זקוקים לראיות והשוואות משלהם. תיקון נתיב ה-API אינו אישור שכל נתיבי המוצר מדויקים.
